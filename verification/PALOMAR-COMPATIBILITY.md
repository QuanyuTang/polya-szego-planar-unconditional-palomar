# Palomar build-directory compatibility

The [first registry verification](https://github.com/PalomarRegistry/PalomarSubmission/actions/runs/39100915545) of commit `cbf34160d21a1b8fa3b8c85e67460eff40d8ff1f` failed at `solution-build`. The mechanical report lists failed EllipticPdes dependency targets and read-only filesystem errors. Its recorded peak memory was about 2.98 GB, with no OOM event. The report retains only the final 20,000 characters of the build output, so it does not preserve the full path context of the original write errors.

The verifier revision was `d4e41c1d5b0d114c4859e6e5831dc6d3ad1d0d44`. Its `manifest_packages`, `package_checkout` and `materialize_packages` functions select writable `.lake/build` and `.lake/config` directories at a Git checkout's root, without incorporating that dependency's `subDir`. The EllipticPdes dependency used `subDir = "lean"`, whose actual Lake output directory is consequently read-only in that sandbox. The earlier repository workflows built the dependencies in a writable environment before kernel comparison and did not test this outer build restriction.

The repair includes exactly the 81 required EllipticPDE modules in `vendor/EllipticPdes`, taken verbatim from upstream commit `ec784093f30308ef770ff855ce624725adf6f870`. The contained package retains their copyright notices, Apache license and upstream Lean options. A minimal Lakefile exposes the required library and the same fixed Mathlib dependency. The root project now uses a contained path dependency, a layout the verifier explicitly grants its own writable build and config directories. No upstream Git dependency or trusted verifier is patched.

`elliptic-vendor.json` records each source path, original Git blob and SHA-256. `scripts/check-release-inputs.py` checks the complete 81-module inventory and hashes, package location, dependency pin and frozen checksum coverage. The 104 original project Lean files, five public statements, original definitions, permitted axioms and 185-target build order are unchanged. The third-party sources remain attributed to their upstream authors.

The added `palomar-official.yml` calls the official reusable workflow at that same immutable verifier revision in full mode against the caller's exact commit. It selects `palomar-standard-v1` on a GitHub-hosted runner; the failed registry run used a Namespace runner. The verifier and confinement code are the same pinned version, while the hardware profile differs. The workflow creates only a CI preflight and its mechanical-report artifact, without registering a result or resubmitting the failed registry request. A successful report is predictive evidence for a subsequent submission, not registry acceptance. Read the actual workflow result and report for the commit under review.
